# API reference (source reviewed 2026-10-21)

The authorization design is source-based; current run results and untested live Supabase boundaries are tracked in `evidence/security-test-results.md` and `docs/security-testing.md`.

Base Edge Function URL: `${SUPABASE_URL}/functions/v1/<function-name>`. Frontend requests send `Authorization: Bearer <Supabase user access token>` and public anon/publishable `apikey`. Every function has gateway JWT verification in `supabase/config.toml`; the handler also calls Supabase Auth `getUser()` before the operation. Actor IDs and roles in request bodies are ignored.

Successful JSON responses are `{ "data": ..., "request_id": "<server UUID>" }`; errors are `{ "error": { "code": "...", "message": "..." }, "request_id": "<server UUID>" }` with `X-Request-Id`. Binary preview/download responses are raw bytes with security headers instead. `OPTIONS` is handled for CORS. The current source allows arbitrary HTTP localhost/loopback ports for development; non-local origins must be explicitly allow-listed in Edge Function secret `ALLOWED_ORIGINS` (no wildcard). On 2026-10-21, an `OPTIONS` preflight from `http://127.0.0.1:4173` to the owner-confirmed dedicated test project returned HTTP 204 and allowed that exact origin. This did not verify authenticated function behavior, production-origin CORS, or that the deployed function matches current source.

Common errors: 400 `invalid_request`/`invalid`; 401 `unauthenticated`; 403 `forbidden`; 404 `not_found` (missing and inaccessible document are intentionally identical), or `grantee_not_found`; 405 `method_not_allowed`; 413 `payload_too_large`; 415 `unsupported_media_type`; 429 `rate_limited`; 409 `conflict` where returned; 503 `unavailable` for some lock/storage failures; 500 `internal`. Do not assume every DB error is mapped to 503: wrapper maps lock-timeout `55P03` and empty DB error code to 503; other unexpected DB failures can map to 500. Request parsing/validation failures may occur before an audit event.

## Edge Functions

`verify_jwt=true` applies to all nine configured functions. Document-level rules are enforced in `app.access_level` / `app.authorize_or_deny` and service functions, not only in frontend controls.

### Audit events

Observed action names include `auth.failure`, `document.upload`, `document.read`, `document.preview`, `document.download`, `document.edit`, `document.replace`, `document.delete`, `document.purge`, `storage.orphan`, `permission.grant`, `permission.revoke`, `permission.recipient_search`, `document.visibility_change`, `admin.role_change`, `admin.audit_query`, `admin.audit_verify`, and `request.rate_limited`. Outcomes depend on operation; not every malformed HTTP request produces an audit row. Audit rows are created by trusted SQL service operations or the verified Edge Function; client-supplied activity text is never accepted. Some historical preview/download successes were recorded at authorization time and cannot establish whether bytes were returned; the admin page labels those legacy entries as unverified delivery. See migrations 0300, 0500, 0700, 0800, 20261020000300 and `supabase/functions/_shared/handlers.ts`.

## Data API / PostgREST reads

Base: `${SUPABASE_URL}/rest/v1/`; browser sends the user's JWT and anon/publishable `apikey`. RLS applies. There are no browser write policies for documents, versions, permissions or audit rows.

- `GET /rest/v1/profiles?select=...`: authenticated user sees own profile, admins see all profiles for administration, and related users may see each other under the share relationship policy. User may update only own `display_name` column; role/email/id are protected.
- `GET /rest/v1/documents?select=<explicit allowed columns>`: owner/current grantee/global signed-in viewer only. Do not use `select=*`; `storage_key` is not granted to clients. Migration 0700 grants `is_global` read.
- `GET /rest/v1/document_versions?select=...`: version metadata only for callers with document read access; storage key is not selectable. Historical byte download is separately authorized by Edge Function.
- `GET /rest/v1/document_permissions?select=...`: grantee's own grants/history or all grants on a document they own.
- `GET /rest/v1/audit_events?select=...`: admins all, users their own events, owners events on their documents, per RLS. No client writes.
- `GET /rest/v1/user_notifications?select=...`: authenticated users may read only their own notification rows. RLS binds the recipient to `auth.uid()`; client writes are revoked.
- `POST /rest/v1/rpc/search_documents`: authenticated SECURITY INVOKER search; filters available by query/category/owner/date/scope/limit/offset. Results are restricted to current access by RLS/helper.
- `POST /rest/v1/rpc/dashboard_stats`: authenticated SECURITY INVOKER counts only accessible documents.
- `POST /rest/v1/rpc/mark_notifications_read`: authenticated user-bound function marks only the caller's notifications read; optional `p_ids` is capped at 100, while omitted/null marks all own notifications read.
- Direct `svc_*` RPCs are not client endpoints; service-role execution only. `app` schema is deliberately not in exposed API schemas.

## Document notifications

Migration `20261020000500_user_notifications.sql` creates trusted database triggers for direct grants, newly global documents and successful document edit/replacement audit events. Each row snapshots the document title and actor display name and is addressable only by its recipient. Realtime INSERT events are published on `supabase_realtime`; the client also polls every 30 seconds for missed events. Existing notices load without historical popups. Selecting a notice marks it read and navigates to the normal document route, which still enforces current access.

## Storage access path

`storage.objects` direct client access is denied for `anon`/`authenticated` by restrictive `documents_bucket_deny_clients`; the `documents` bucket is private, 10 MiB, PDF/PNG/JPEG. Edge Functions verify/audit authorization via `svc_*`, then access bytes using service-role SDK. No signed URLs are issued. Tests in `supabase/tests/db/rls.test.ts` exercise SQL policy/shim behavior; real Supabase Storage API behavior is not covered by that shim and needs live integration testing.
